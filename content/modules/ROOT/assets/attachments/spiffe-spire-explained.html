Chapter 1 · the standard and the implementation

SPIFFE and SPIRE, for dummies

Today a pod proves who it is with a secret: a password, an API key, a client secret. Secrets get copied, leaked into git, and replayed from a laptop. Whoever holds the secret is the workload.

SPIFFE replaces what you know with what you are, proven by the platform you run on. SPIFFE is the spec (ID format, document formats, Workload API). SPIRE is the software that implements it. ZTWIM is Red Hat's operator that runs SPIRE on OpenShift.

Think of it as

A passport office. You never fill a form with your own name. The consulate looks at you and prints the passport. You can't ask for somebody else's.

Chapter 2 · Red Hat's operator

Zero Trust Workload Identity Manager

ZTWIM is a supported operator that runs SPIRE for you. You don't run Helm. You create a handful of custom resources, all named cluster, and the operator reconciles everything in zero-trust-workload-identity-manager. Package openshift-zero-trust-workload-identity-manager, channel stable-v1.

Our cluster not installed

v1.1.3 is in the redhat-operators catalog. oc get crd | grep -i spire returns nothing (Robert, verified 2026-11-19).

Known to work tested upstream

OpenShell token exchange tested on ROSA 4.21 with ZTWIM v1.1.0 (PR #1970 review, with small ClusterSPIFFEID tweaks).

The resources, in the order the docs require

1ZeroTrustWorkloadIdentityManagerSets trustDomain (immutable, use the apps domain), clusterName, bundleConfigMap.
2SpireServerStatefulSet with the server and the Controller Manager side by side, plus a PVC. jwtIssuer, caValidity 24h, X.509 1h, JWT 5m.
3SpireAgentDaemonSet. k8sPSATEnabled node attestation, k8sEnabled workload attestation.

5SpireOIDCDiscoveryProviderDeployment + Route. Publishes the JWKS so Keycloak, Vault, Entra or Authorino can verify JWT-SVIDs.
+ClusterSPIFFEIDWhich pods get which SPIFFE ID. Robert calls it the Agent Registry.
+ClusterFederatedTrustDomainTrust another domain. Can't be turned off once enabled.
Three values must line up

SpireAgent.socketPath = SpiffeCSIDriver.agentSocketPath · SpiffeCSIDriver.pluginName = SpireOIDCDiscoveryProvider.csiDriverName = the pod's driver: · SpireServer.jwtIssuer = SpireOIDCDiscoveryProvider.jwtIssuer, which becomes the iss every verifier trusts.

The OIDC bridge, same pattern every time

The docs show it with Vault (vault write auth/jwt/config oidc_discovery_url=…, role bound to sub: spiffe://…/ns/demo/sa/client) and with Azure Entra (audience api://AzureADTokenExchange). Keycloak is just one more relying party: SPIRE issues → OIDC provider publishes keys → relying party trusts the issuer → SVID is exchanged for a local token.

Chapter 3 · OpenShell dynamic token grants

How a sandbox gets an SVID and trades it

Module 2 already teaches the core trick. With --provider maas, OpenShell gives the agent an opaque placeholder and swaps in the real key at the egress proxy. Token grants go further: the supervisor mints the real token on demand from the sandbox's SPIFFE identity, so nothing is stored at all.

Upstream v0.0.113+

token_exchange landed in PR #1970 (merged 2026-08-24). The shared-supervisor SPIRE Broker API (PR #4732) is merged but not released yet.

Chapter 5 · two roots of trust

Keycloak, OpenShell and SPIRE: who trusts whom

SPIRE signs workload identity. Keycloak signs user identity and permissions. Keycloak bridges the two: it accepts a SPIRE-signed SVID as the client's proof and mints its own token naming both. Authorino only ever has to trust Keycloak.

Keycloak's SPIFFE support, for real

Issue #41907 was closed as a duplicate of epic #42634, Federated client authentication. There is no special SPIFFE authenticator. Instead:

Identity provider type spiffe, with trustDomain and bundleEndpoint (a SPIFFE bundle or the OIDC JWKS URL from ZTWIM).
Client authenticator federated-jwt ("Signed JWT - Federated"), with jwt.credential.issuer = IdP alias and jwt.credential.sub = the SPIFFE ID.
Assertion type urn:ietf:params:oauth:client-assertion-type:jwt-spiffe, with aud = the realm issuer URL.

Blocker not ours

The Keycloak is RHDP-provisioned and shared by every realm. Turning on a preview feature means a server restart nobody in the lab owns. Ask RHDP, run a lab-owned Keycloak for the spike, or use the Authorino fallback.

Open question design

Keycloak wants one unique SPIFFE ID per client. OpenShell sandbox IDs end in a UUID per sandbox. How do you register clients for sandboxes that come and go?

Chapter 6 · the enforcement point

MCP Gateway: one more predicate

The MCP Gateway doesn't speak SPIFFE, and it doesn't need to. It's Envoy with a Kuadrant AuthPolicy, and Authorino validates JWTs from an OIDC issuer. Each tool call crosses two listeners (tenant-policy/templates/mcp-gateway-policy.yaml):

Try the intersection rule. Pick a token and a role assignment:

patternMatching (predicates are AND-ed)
403

Option 1 · indirect (recommended)

SPIFFE authenticates the agent to Keycloak. The exchanged token carries sub=operator and azp=agent. Authorino keeps trusting only the realm and adds has(auth.identity.azp) && auth.identity.azp == 'hermes-agent'. With OpenShell, azp is the sandbox SPIFFE ID, so match a prefix instead.

Option 2 · direct (fallback)

The mcp listener validates a JWT-SVID from customHeader: x-agent-svid with issuerUrl = the SPIRE OIDC provider. The mcps listener keeps validating the operator token. That's two independent roots and no Keycloak change at all. The catch: the two facts are never bound into one artifact.

Attribution, not just authorization

The jti already in the token becomes the join key across the Authorino decision log, the plant-api audit row, raised_by_verified (kept beside the model-written raised_by on purpose) and the MLflow trace tags. Model the actor as an ordered list from day one, so moving to RFC 8693 act later is cheap.
